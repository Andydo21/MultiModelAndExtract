\begin{abstract}
Question answering over technical manuals and specification sheets requires every value to stay attached to the right subject, table column, heading scope and footnote condition. We present a retrieval-augmented system that performs layout, table and figure analysis offline and gives the generator compact, explicitly scoped evidence as text. Offline, pages are read by a vision--language OCR model, tables are reconstructed cell by cell, and the result is projected into a source-bound per-document graph indexed with BM25, dense text vectors and figure-level ColPali vectors. Online, a hybrid retriever fuses the channels, selects seeds by question-part coverage and novelty, expands them within the seed's document snapshot, and serializes them as \emph{Hierarchical Evidence Pods} with table grids, merged-cell metadata and stable citation IDs. In a pilot evaluation involving 50 questions over 20 technical documents, the production pipeline achieved a Hit@1 of 0.80, an MRR of 0.87, and a required-evidence recall of 0.955. Using text-only input to a zero-shot 7B vision-language model, the system achieved an answer accuracy of 0.800, an attribute leakage rate of 0.051, and a citation faithfulness score of 0.89. Small-scale controlled experiments further suggest that scope-aware graph expansion can reduce context length while retaining required evidence, and that structured OCR text can be competitive with direct image input under the evaluated settings.
\keywords{Document question answering \and Retrieval-augmented generation \and Table understanding \and Knowledge graph \and Hybrid retrieval \and Evidence packaging}
\end{abstract}

\section{Introduction}
Retrieval-augmented generation (RAG)~\cite{lewis2020rag} lets a language model answer from documents it was not trained on. Technical documents, however, are not running prose: product variants share one specification table, limits are qualified by footnotes, and the heading above a table decides which device a value belongs to. When such pages are cut into fixed-length text chunks, row--column alignment and heading scope disappear, and a generator can attach a value to the wrong subject---an error we call \emph{attribute leakage}. Reading the page image with a vision--language model (VLM)~\cite{mathew2021docvqa,bai2025qwen25vl} keeps the layout but spends a large number of visual tokens per page and still leaves the model to infer which value belongs where.

This work takes a different position: the expensive structural analysis is done once, offline, and its result is preserved explicitly in the evidence given to the generator, \emph{as text}. Visual models are used where they are cheap and decisive---layout analysis and OCR offline, and ColPali as a \emph{retrieval} channel that locates relevant figures---while the online generator receives only structured text. The system (Fig.~\ref{fig:arch}) consists of an offline extraction stage and an online retrieval and answering stage. Our contributions are:
\begin{itemize}
\item \emph{Hierarchical Evidence Pods}, a structure-preserving evidence serialization that groups source regions by document, reading stream, and heading path; represents validated table grids with merged-cell metadata; and retains stable source identifiers for traceable citations. This representation aims to preserve contextual relationships among subjects, attributes, values, and qualifying conditions when supported by the extracted document structure;
\item \emph{scope-aware graph expansion} over a source-bound per-document graph built offline, in which seeds chosen for question-part coverage and novelty are expanded only inside their document snapshot and heading scope, and similarity or model proposals are kept as candidates rather than facts;
\item a \emph{source-grounded question-answering pipeline} in which the generator receives text only and returns claims whose citations are checked against the supplied source IDs;
\item a pilot evaluation on 50 questions, reporting the production pipeline and small controlled examples on frozen inputs for evidence format, graph expansion and visual input, with all reruns reported.
\end{itemize}

\section{Related Work}
\textbf{Document understanding.} Layout-aware encoders such as LayoutLMv3~\cite{huang2022layoutlmv3} pre-train text, layout and image jointly, but are fine-tuned per task and keep the structure implicit in their representations; DocVQA~\cite{mathew2021docvqa} benchmarks QA on page images. We instead use off-the-shelf layout and table models and make the structure explicit, as text that any generator can read. Surya~2~\cite{paruchuri2026surya2} provides layout analysis, OCR and reading order, and the Table Transformer (TATR)~\cite{smock2022pubtables} detects table rows and columns.
\textbf{Retrieval.} BM25~\cite{robertson2009bm25} remains strong for identifiers; BGE-M3~\cite{chen2024bgem3} provides multilingual dense embeddings; ColPali~\cite{faysse2025colpali} retrieves page images through late interaction over patch embeddings. Reciprocal rank fusion (RRF)~\cite{cormack2009rrf} combines rankings without score calibration.
\textbf{Structure for LLMs.} GraphRAG~\cite{edge2024graphrag} builds entity graphs for corpus-level summarization; table serialization strongly affects LLM table understanding~\cite{sui2024table}; long contexts are used unevenly by LLMs~\cite{liu2024lost}. Our graph is per document and source-bound: it supplies scope and neighbours for retrieved regions rather than generated summaries. Query decomposition follows least-to-most prompting~\cite{zhou2023leasttomost}.

\subsection{Offline Extraction}
Extraction runs in two phases (Algorithm~\ref{alg:extract}): a per-page phase that reads and stores each page as soon as it is rendered, and a whole-document phase that runs only after every page is available, because hierarchy, entity identity, similarity links and the graph depend on the complete document.

\begin{algorithm}[t]
\caption{Offline extraction pipeline (one document version)}\label{alg:extract}
\begin{algorithmic}[1]
\For{each page $p$}
  \State render $p$ at 150 and 300\,DPI (native parse for Office files)
  \State Surya full-page pass $\rightarrow$ regions, text, reading ranks \Comment{cached}
  \State one inner layout/OCR pass per figure crop
  \State tables: TATR grid + per-cell OCR; validate or mark unresolved \Comment{cached}
  \State persist the page's source regions in one transaction
  \State ColPali-embed figure crops of $p$ \Comment{background, or deferred}
  \State rebuild the source tree (hierarchy, reading streams)
\EndFor
\If{some page failed} \State keep the stored pages; stop without dense indexing or graph \EndIf
\State check reading order; GLiNER entity spans; GLiNER2 same-name identity
\State BGE-M3 dense index of all source regions
\State \texttt{RELATED\_PASSAGE} links (BGE-M3, reranker, GLiNER2)
\State retry failed ColPali pages once
\State project, compact, validate and publish the Neo4j snapshot
\State prune older graphs and vectors; rebuild the BM25 postings snapshot
\end{algorithmic}
\end{algorithm}

Page results are cached under a key formed from the page image hash and the OCR policy, so an interrupted or repeated run reuses completed pages and re-reads only failed ones; vector identifiers are deterministic, so a retry overwrites rather than duplicates points. A Surya region is never split: each region is one source. Text from native Office parsing, which has no region boundaries, is split into segments of at most 900 characters at sentence or word boundaries, and consecutive segments of the same source under the same heading are re-joined up to that size. Figure embedding can overlap the per-page phase or run later as a backfill; the dense index waits for the complete tree so that every source carries its final heading path. Every stored region can be inspected against its page in the deployed interface (Fig.~\ref{fig:extract} is drawn from these stored regions).



\textbf{Page rendering and layout.} Each PDF page is rendered twice, at 150\,DPI for page analysis and at 300\,DPI for text inside figures and for table structure; the PDF text layer is not used, so scanned and born-digital files follow the same path. Word, PowerPoint and spreadsheet files are parsed natively, keeping their own tables and embedded images. Surya~2~\cite{paruchuri2026surya2} (checkpoint \texttt{datalab-to/surya-ocr-2}), a compact vision--language OCR model that we serve locally with llama.cpp, reads the page in a single full-page pass that returns layout regions (title, paragraph, list, table, figure, caption, header/footer, footnote), their text and their reading order. Each region becomes one \emph{source} carrying its text, page number and bounding box. A crop whose decoding loops or exhausts its token budget is retried once with wider framing and a larger budget; figure-text crops get one further low-temperature, contrast-enhanced attempt. Regions that still fail stay flagged and are excluded from retrieval and entity extraction, and a document with a failed page is not published to the graph.

\textbf{Tables.} Table regions are cropped from the 300\,DPI rendering. TATR~\cite{smock2022pubtables} (\texttt{microsoft/table-transformer-structure-recognition}, a DETR detector with a ResNet-18 backbone) predicts columns, rows and spanning cells, which are reconciled with ruling lines visible in the crop, and every non-empty cell is read separately by Surya OCR (one enlarged retry for empty readings). The grid is accepted as \emph{cell-aware} only if it is complete and consistent---no holes, no overlapping cells, spans inside the grid, at most 200$\times$64 cells; the source text is then rebuilt from the cells, header rows and merged cells are stored as metadata, and the page OCR is kept for audit. Otherwise the table is \emph{unresolved}: no row/column text is published for it, and it can reach a generator only as an image crop.

\textbf{Figures.} Each page-level figure gets exactly one extra layout and OCR pass on its 300\,DPI crop. Page text overlapping the figure is masked first so that it keeps its own owner, and nested pictures are not scanned again. Every text region found inside becomes its own source, a child of the figure with a separate reading scope, marked as single-pass OCR. A caption that Surya places inside the figure region is attached to it; nearby captions and paragraphs are only linked by geometry as \emph{candidates} (\texttt{FIGURE\_CAPTION\_CANDIDATE}, \texttt{FIGURE\_NEAR\_TEXT\_CANDIDATE}), because proximity does not prove that a caption describes a figure. No free-form image description is generated.

\textbf{Hierarchy.} Heading levels are taken only from the model output or the native file; a heading with an unknown level is placed directly under the document rather than at a guessed depth. Tables, figures and their children are nested under the current heading, whereas page headers, footers and footnotes are attached to the document root. Sources are ordered by Surya's ranks within each page or figure scope; if the ranks are missing or ambiguous, the heading stack is reset instead of guessing an order.

\textbf{Entities.} Entity spans are proposed by the GLiNER-RelEx checkpoint \path{knowledgator/gliner-relex-multi-v1.0}~\cite{knowledgator2025relex}, which uses the GLiNER architecture~\cite{zaratiana2024gliner}; we use it for named-entity spans only (organisations, people, products and models, components, protocols), collapsed into a single entity type. A batch is accepted only if every span reproduces the source text exactly at its offsets, does not overlap another span and scores at least 0.5; relation output is rejected at this stage. Accepted spans become \texttt{MENTIONS} edges, and mentions with the same name inside one document are linked to one entity only when the GLiNER2 classifier \texttt{fastino/gliner2-base-v1}~\cite{zaratiana2025gliner2} judges them to denote the same thing in context. Model-proposed relations between passages are not published. The language model is not used in this stage.

\textbf{Related passages.} For every source, BGE-M3 proposes five similar sources in the same document; a pair becomes a \texttt{RELATED\_PASSAGE} edge only if the cross-encoder logit is non-negative and a GLiNER2 topic check agrees, with at most two links per source. These edges support navigation and are never treated as references.

\textbf{Graph projection.} Each extraction run is projected into Neo4j as a snapshot keyed by tenant, contract, version, run and source fingerprint; edges never cross snapshots. Node categories are \texttt{structure} (document and section headings), \texttt{layout\_block}, \texttt{evidence} (one per source region), \texttt{table\_row}/\texttt{table\_cell}, \texttt{source\_image}, \texttt{visual\_embedding} and \texttt{entity}. Table~\ref{tab:graph} lists every relation, the tool that produces it and its size on the pilot documents, and Fig.~\ref{fig:extract} shows the regions and graph size for one datasheet page. Each relation records its origin, and only relations derived from the source layout are treated as structure; proximity and similarity relations are stored as candidates. No relation is created by the language model.

\textbf{Edge construction rules.} Each relation is created by a fixed rule, and an edge whose condition cannot be established is omitted rather than guessed. \texttt{CONTAINS} follows a heading stack driven by supplied levels (a heading of level $\ell$ closes all open headings of level $\geq\ell$; inner figure regions hang under their Surya parent). \texttt{NEXT} links consecutive sources of one page or figure scope only if all ranks are distinct non-negative integers and none is unresolved; otherwise the group gets no \texttt{NEXT} edges. Tables get one row node per grid row and one cell node per cell with its row, column, spans and header flag. On normalised page coordinates (0--1000), \texttt{LEFT\_OF} and \texttt{ABOVE} keep only the nearest right-hand and lower block whose gap is at most 80, whose extents overlap by at least half and whose connecting corridor is not crossed by another block; a caption or paragraph that is such a neighbour of a figure, or one of its two closest unobstructed blocks, becomes a caption or near-text candidate. A \texttt{MENTIONS} edge stores the exact span and score ($\geq$0.5) of a mention; page headers and footers produce none. Same-name mentions are paired and GLiNER2 judges each pair in a window of about 900 characters: \emph{same} needs a score $\geq$0.9 and a margin of 0.1 over \emph{different}, a confident \emph{different} forbids the merge, and accepted pairs are merged by union--find, highest score first, so two different names never share an entity node. \texttt{RELATED\_PASSAGE} and \texttt{HAS\_EMBEDDING} follow the conditions in Table~\ref{tab:graph}.

\textbf{Publication checks.} A document is published only if every page was read and the whole-document analysis finished on the same source fingerprint. The projection is compacted (redundant cell paths and duplicate generic links removed) and validated (unique node keys, every node and edge endpoint inside the snapshot), then replaced in a single Neo4j transaction that also prunes older snapshots, so readers never see a half-written graph. Online, structural relations and shared \texttt{MENTIONS} drive expansion, \texttt{HAS\_FIGURE\_TEXT} and caption candidates serve figures, and \texttt{RELATED\_PASSAGE} is used only after re-ranking; geometric relations and table rows/cells are not passed to the generator, because the pods already present tables as grids.

\textbf{Indexes.} Three retrieval indexes are built per version (ColPali serves retrieval only; its vectors are never given to the generator): a BM25~\cite{robertson2009bm25} index over token postings stored in PostgreSQL; 1024-dimensional BGE-M3~\cite{chen2024bgem3} dense vectors of source regions in Qdrant; and ColPali multi-vectors computed only for figure crops, using the \texttt{vidore/colpali-v1.2} checkpoint released with~\cite{faysse2025colpali}. Text and table regions never fall back to full-page visual embeddings. Each figure vector is linked to its layout block in the graph through \texttt{HAS\_EMBEDDING}.

\textbf{Role of ColPali.} ColPali embeds the figure image itself: its vision encoder turns the crop into patch-level vectors, and a text query is scored against them by late interaction (MaxSim over query tokens and patches). It plays two roles. (1) \emph{Text-to-image search}: a question can reach a diagram, wiring drawing or labelled photo even when the figure's OCR text is sparse, misread or worded differently from the question. (2) \emph{Bridge from figures to text}: a retrieved figure is not passed to the generator as pixels; instead the graph connects it to the document's passages. Its in-figure text regions (\texttt{HAS\_FIGURE\_TEXT}) carry \texttt{MENTIONS} of entities, and passages elsewhere in the document that mention the same entities are added as context, together with caption candidates. The generator thus receives the figure as its OCR text, caption candidates and the passages that discuss the same components, all as text.

\subsection{Online Retrieval}
\textbf{Query planning.} In one call, the generator (Qwen2.5-VL-7B-Instruct, AWQ, served with vLLM~\cite{bai2025qwen25vl,kwon2023vllm}) splits the question into answer parts with retrieval queries, the reading scope and whether images are needed. If planning fails, retrieval uses the original question and records the planner as unavailable.

\textbf{Hybrid retrieval and fusion.} Every retrieval query is sent to all three channels over the latest versions the user may read. Candidate lists are fused with equal-weight RRF~\cite{cormack2009rrf},
\begin{equation}
\mathrm{RRF}(d)=\sum_{m\in\{\mathrm{BM25},\,\mathrm{dense},\,\mathrm{ColPali}\}}\frac{1}{k+r_m(d)},\qquad k=60,
\end{equation}
where $r_m(d)$ is the rank of $d$ in channel $m$ (terms are omitted when $d$ is absent). We use $k=60$, the value proposed and found robust by Cormack et al.~\cite{cormack2009rrf}, and equal weights because the three channels have no calibrated scores; neither was tuned on the pilot set. All fused candidates are then scored together by the multilingual cross-encoder \texttt{BAAI/bge-reranker-v2-m3} of the BGE family~\cite{chen2024bgem3}, always paired with the original request.

\textbf{Seed selection.} Seeds are chosen greedily. Let $P_i$ be the answer parts that candidate $i$ was retrieved for, $C$ the parts already covered, $\rho_i=\max_r 1/(1+\log_2 r)$ over its ranks, $o_i$ its maximum token Jaccard overlap with already selected seeds and $D$ the set of documents already used. The next seed maximizes, lexicographically,
\begin{equation}
\bigl(\,|P_i\setminus C|,\;\rho_i-0.35\,o_i+0.05\,[\mathrm{doc}_i\notin D],\;\textstyle\sum_r 1/(60+r)\bigr),
\end{equation}
up to $\min\!\bigl(24,\max(|\text{parts}|,\,3\cdot\text{groups})\bigr)$ seeds. Coverage of unanswered parts always comes first. The coefficients are heuristic values set during development and not tuned on the pilot set: 0.35 makes a near-duplicate of an existing seed lose against a moderately lower-ranked but different source, and 0.05 is a small tie-breaking bonus for a new document that cannot outweigh a clear rank difference. The upper bound of 24 is the default answer-source limit of the deployed configuration. Similar passages are down-weighted rather than discarded, so different versions, quantities and conditions remain available.

\textbf{Graph expansion.} For each seed, Neo4j returns neighbours within the same snapshot: sources reached through a direct structural relation of the seed's block (excluding the document root), sources sharing an entity mention, figure-text and visual-explanation links, and \texttt{RELATED\_PASSAGE} neighbours. Scope-aware expansion admits structural neighbours only inside the seed's heading scope. Similarity-only neighbours are admitted only if they pass re-ranking against the question. Expanded sources are deduplicated and ordered by reading position.

\subsection{Hierarchical Evidence Pods}
Selected sources are serialized as pods (Algorithm~\ref{alg:pods}, Fig.~\ref{fig:pod}).
\begin{enumerate}
\item \textbf{Scope grouping.} Sources sharing document, version, file name, reading stream and heading path form one pod, printed once as a header (``Source scope $k$ \textbar{} Document/version $j$ \ldots{} Heading: A $>$ B $>$ C''). The heading path is fixed at extraction time from the source tree.
\item \textbf{Table grids.} Cell-aware tables are rendered as Markdown grids. Header rows are declared; if no header was detected, neutral column labels are used instead of guessing one. Merged cells are \emph{not} duplicated: they are listed as span metadata, so the model is told which cells span rows or columns rather than receiving copied values that the source does not repeat. An unresolved table carries no row/column text, only its status and the reason it was rejected.
\item \textbf{Figures.} Figure sources carry their in-image text, caption and location; figure--text links are presented as proposals.
\item \textbf{Links and IDs.} Each source keeps a stable ID (version, run, region). Graph links between selected sources are listed once next to their first source with direction and review status; structural machinery such as \texttt{HAS\_CELL} is not serialized.
\end{enumerate}
The pod in Fig.~\ref{fig:pod} shows how the four parts of a fact stay together. The \emph{subject} is given by the scope header (document LPH\_E, heading ``Specifications''), the \emph{attribute} and \emph{value} by one grid row (``Cycle time (*2)'' $\rightarrow$ ``0.45\,sec''), and the \emph{condition} by the footnote *2 in the same scope (2\,kg payload, two points 300\,mm apart, 25\,mm height). In flat chunking the footnote is a separate chunk without the product name, and the row loses its column header; the pod keeps all four under one ID-labelled scope, so the generator can cite the value and its condition together.

The generator returns claims (subject, attribute, value, condition, source IDs). Code checks that every cited ID was supplied and that the format is valid, with a single format-repair retry; it does not verify semantic correctness. If the prompt exceeds the context window (16{,}384 tokens), the output budget is reduced first and sources are then split into groups whose findings are combined against the original cited sources. The pods are plain text: a figure retrieved through ColPali reaches the generator as its in-image OCR text, caption candidates and location, so the answering step needs no image input. The deployed system can optionally attach the figure or unresolved-table crop when the generator is a VLM; this option is disabled in all text-input experiments, and image input is studied only in E4.

\begin{algorithm}[t]
\caption{Evidence pod serialization}\label{alg:pods}
\begin{algorithmic}[1]
\Require selected sources $S$ (ordered), graph context $G$
\State $\mathcal{P}\gets$ ordered map from scope to list
\For{$s \in S$}
  \State $h\gets$ heading path of $s$; drop last element if $s$ starts with it
  \State $\kappa\gets(\text{doc},\text{version},\text{name},\text{reading stream},h)$
  \State $r\gets\{\text{id}(s)\}$; add review/OCR/table warnings
  \If{$s$ is a table and cells reproduce its OCR text}
    \State $r.\text{grid}\gets$ rows; $r.\text{header}\gets$ header rows; $r.\text{spans}\gets$ merged cells
  \Else \State $r.\text{text}\gets$ text of $s$ \EndIf
  \State append $r$ to $\mathcal{P}[\kappa]$
\EndFor
\State $L\gets$ edges of $G$ between selected sources (semantic, figure, similarity)
\State \Return render($\mathcal{P}$, $L$)
\end{algorithmic}
\end{algorithm}

\section{Experimental Protocol and Results}
\subsection{Setup}
\textbf{Corpus and questions.} The deployed index contains 201 document versions. The pilot set has 50 questions on 20 English technical documents (robot, controller, spark-plug, A/C service and wiper product literature) with reference answers, subject--attribute--value--condition tuples and gold evidence regions: 73 question--region pairs over 65 distinct regions (1.46 per question; 33 questions have one gold region, 17 have two to four, and seven regions serve more than one question), including 21 pairs over 16 distinct tables. All metrics count question--region pairs. Categories (a question may have several): condition 31, table 18, comparison 13, footnote 11, procedure 7, identifier 5, figure text 3, multi-document 2. Gold answers were checked against the evidence text. The documents were also used during development, so the set is a pilot rather than an independent test set. Questions referred to by ID are listed in Table~\ref{tab:questions} with their reference answers and the label of the system's answer.

\textbf{Inputs.} The production main flow runs the full deployed pipeline, including retrieval, live on the index of all 201 versions. For the controlled ablations and the ColPali counts, retrieval is run once with the same pipeline (top-10 \texttt{query\_match} sources per question) and frozen together with graphs exported from Neo4j before any generation, so every configuration sees identical inputs. Regions duplicated across uploads of the same PDF are matched by content hash in another version.

\textbf{Hardware.} The generator and ColPali are served on two NVIDIA Tesla T4 GPUs (15\,GB each; 10.0\,GB and 5.9\,GB in use while serving); vLLM runs with a memory utilisation of 0.8, giving a KV-cache pool of 38{,}448 tokens. Extraction models (Surya, TATR, GLiNER-RelEx, GLiNER2, BGE-M3 and the reranker) run on a local RTX~3050 Ti laptop GPU with 4\,GB.

\textbf{Generation.} Qwen2.5-VL-7B-Instruct-AWQ on vLLM ($16{,}384$-token context), temperature 0, max 2048 output tokens, one run per configuration (with temperature 0, 62 of 71 ablation configurations that were repeated gave identical outputs). The generator is a VLM; ``text-only'' in this paper means that no image is attached to its prompt, not that a model without a vision encoder was used. The production main flow uses the deployed prompts and checks; the controlled ablations use a fixed JSON-schema output whose citation field is restricted to the supplied IDs. Prompt tokens are counted with the served model's tokenizer (revision \texttt{536a357}) and checked against API usage; sources are never truncated or padded.

\textbf{Experiments.} \emph{E1 (evidence format)}: the same evidence, order and model under A flat text, B JSON, C Markdown tables, D C+breadcrumb, E full pods; with gold evidence and with top-5 retrieved evidence. \emph{E2 (graph expansion)}: fixed top-3 retrieved seeds, one 6{,}000-token ceiling, modes A none, B previous/next blocks, C structural (B + parent heading, siblings, figure--text links), D scope-aware (C restricted to the seed's heading scope). \emph{E4 (visual input)}: full-page images, evidence crops, OCR text only, and OCR+caption structured pods, on questions with tables or figures; visual tokens are measured as API prompt tokens minus the tokenizer count of the same messages without images.

\textbf{Metrics and denominators.} \emph{Retrieval}: Hit@1 and mean reciprocal rank (MRR) of the first gold region among the retrieved sources; evidence recall and precision over the first ten sources (R@10, P@10); required-evidence recall over all sources sent to the generator. \emph{Citations}: citation precision (cited sources that are gold) and citation recall (gold regions cited). These are computed per question and averaged over questions. \emph{Answers}: answer accuracy over answers (correct 1, partial 0.5, wrong or no answer 0); strict accuracy counts only correct answers; attribute leakage rate (ALR) is the share of \emph{claims} that bind a value or condition to the wrong subject; citation faithfulness is the share of claims stated by the sources they cite; key-value recall is the share of gold numbers and codes from the tuples that appear in the answer (strict string match), over the questions whose tuples contain such values. Prompt tokens, visual tokens and latency are taken from the logs. Retrieval, citation, key-value and cost metrics are computed deterministically from the logs.

\textbf{Grading procedure.} Answer labels, leakage and faithfulness were assigned in a single LLM-assisted reading pass (Claude, Anthropic), which compared every answer with its reference answer, tuples and gold evidence, following a fixed rubric: \emph{correct} if every requested part is stated with the right value and condition, \emph{partial} if a requested detail is missing or one claim is wrong while the rest is right, \emph{wrong} otherwise, and \emph{no answer} if the model declines to answer; each claim is then checked for leakage and for support by its cited sources. The labels were then reviewed by the first author against the same material, and the review agreed with them. The grading was not blind to the system and no second, independent grader was used, so inter-annotator agreement was not measured; two independent human graders are planned for the full evaluation.

\subsection{Results}
\textbf{Runs.} Each of the 50 pilot questions was run once through the deployed pipeline with text-only generator input, zero-shot (no fine-tuning, no in-context examples). Five answers were obtained in a second run: four (P047--P050) after a temporary server outage and one (P007) after an output-language check that had rejected its first answer was removed. All metrics are reported over the 50 questions (Table~\ref{tab:mainflow}).

\textbf{Retrieval.} The first-ranked source was a gold region for 40 of the 50 questions (Hit@1 0.800; MRR 0.869). On average 90.5\% of a question's gold regions were among its first ten sources (R@10; complete for 41 of 50 questions), and 95.5\% were placed in the generator context after graph expansion (required-evidence recall). P@10 is 0.126 against a ceiling of 0.146, since a question has 1.46 gold regions on average: the context is deliberately broader than the minimal evidence (31.0 sources per question).

\textbf{ColPali.} ColPali returned figure candidates for every question; 22\% of the top-ten sources (111 of 498, in 35 of 50 questions) were found by ColPali alone and by neither text channel, and the figure-to-text bridge added 52 passages in 10 questions. These numbers show that the visual channel \emph{diversifies the candidate pool}; they do not show a retrieval gain. In this pilot no gold region arrived only through the visual channel. The three figure questions are P010 (labels A and G of the Iridium Racing electrode diagram; partial), P028 (components of the COBOTTA Camera Built-in Set; correct) and P046 (function of the multilayer shim and meaning of NVH in the brake-pad kit diagram; correct). In all three, every gold region is text printed in or beside the figure and was found by both BM25 and dense retrieval; ColPali placed one figure candidate in the top ten for P010 and three for P046, none of them gold, and none for P028. The reason is the test material rather than the channel: the pilot corpus contains no document whose answer lies only in a figure without readable text (for example, an unlabelled wiring diagram or a photo of a part), which is the case ColPali is meant for, so the pilot cannot yet demonstrate its effectiveness. With no such questions and no run without ColPali, we make no claim that ColPali improves recall; a set of figure-only questions is planned for the full evaluation.

\textbf{Citations.} On average 83.9\% of a question's cited sources were gold regions (citation precision) and 81.0\% of its gold regions were cited (citation recall). Every answer cited only IDs that had been supplied, which is what the code check enforces; this does not mean that every citation supports its claim: 11 of the 98 claims were not supported by their cited sources (e.g., P009 in Table~\ref{tab:answers}).

\textbf{Answer quality.} The generator answered 33 of 50 questions correctly and 14 partially, with two wrong answers and one abstention, giving an answer accuracy of $(33 + 0.5\times 14)/50 = 0.800$ (80.0\%) and a strict accuracy of $33/50 = 0.660$. The 50 answers contain 98 claims; 5 of them bound a value or condition to the wrong subject (ALR $5/98 = 0.051$), and 87 were stated by the sources they cited (citation faithfulness $87/98 = 0.888$). Most partial answers omit one requested detail of a multi-part question rather than state something false. By category, the 18 table questions reached an accuracy of 0.833 (13 correct, 4 partial, 1 wrong: P048), with required-evidence recall 0.958; the footnote questions were the weakest (11 questions, accuracy 0.636, required-evidence recall 0.795), and condition questions reached 0.774 (31 questions). In all 20 questions whose gold evidence includes a table, every gold table (21 of 21 question--table pairs, 16 distinct tables) was retrieved and placed in the generator context together with its scope. The table questions referred to by ID are P013, P037, P040, P044 and P048 (Tables~\ref{tab:answers} and~\ref{tab:questions}).

\textbf{Text-only reading.} With text-only input, answers reproduced 82.6\% of gold numbers and codes (key-value recall over the 24 questions whose tuples contain such values; 18 of 24 complete), 80\% on identifier questions and 82\% on table questions, without any image reaching the generator.

\textbf{Error analysis.}\label{sec:errors} We read the six text-only answers below full key-value recall. P048 is wrong although its gold table was ranked first: the model returned the product-line name ``Beam Wiper Blades'' instead of the four part numbers and cited a block holding only a URL. Two are correct and are missed by the strict string match (P044 gives ``+110, $-$102'' without the degree sign; P005 writes ``2,000 W''). Two are incomplete rather than wrong: P037 states the 25\,mm height of the cycle-time footnote but omits the 2\,kg load and 300\,mm distance, and P034 names the robots and arm count but not the RC8A controller. In P009 the footnote holding the answer was not retrieved; the model stated that the documents do not cover the case instead of inventing a value, but cited an unrelated reference list, so this answer is also a citation failure. Footnote and condition questions are the weakest group (67\% and 78\% key-value recall). None of these six answers attached a value to the wrong subject; the leaking claims occur elsewhere, e.g., P010 (Table~\ref{tab:answers}) and P050, where RC8A, the controller, is described as a protective box.

\textbf{Unresolved error types.} Three structural error types remain open and are not fixed by the current pipeline. (1) \emph{Footnote scope}: regions labelled as footnotes are attached to the document root, so a footnote can land in a different pod from the table it qualifies and reaches the generator only when retrieval returns it as well. (2) \emph{Multi-level table headers}: a two-level header is not represented explicitly, and the generator can bind a value to the wrong header branch; in P040 every input read the 7\,kg and 6\,kg values but assigned them to the wrong configuration (standard vs.\ robot fitted with jacket). (3) \emph{Incorrect heading assignment}: blocks that do not belong to a heading, such as contact blocks at the page bottom (Fig.~\ref{fig:extract}), are attached to the preceding heading and enter its scope.

\textbf{Worked examples.} The controlled ablations (fixed evidence and generator prompt) are reported on four questions each, namely those for which every configuration had completed, with E1 additionally run on five table questions; they illustrate behaviour and are not powered for significance.

\emph{E2 graph expansion} (Table~\ref{tab:e2}). Expansion matters when retrieval misses part of the evidence: for P007 the three seeds held one of two gold regions (R@10 0.50 in mode A) and a single previous/next step recovered the other. Structural expansion admitted 13--28 sources and approached the 6{,}000-token ceiling, whereas scope-aware expansion rejected 17--96 candidates (mostly outside the seed's heading scope), kept the recovered evidence and used 34--62\% fewer tokens than structural expansion, with 3.5--8.6$\times$ lower graph latency. The simpler previous/next mode, however, used fewer tokens than scope-aware expansion on all four questions (P003: 1{,}934 vs.\ 2{,}079; P007: 1{,}339 vs.\ 3{,}468; P022: 3{,}033 vs.\ 3{,}739; P027: 2{,}158 vs.\ 3{,}840) and also recovered P007's missing region. The token saving of scope-aware expansion is therefore relative to structural expansion; on these four questions it did not beat previous/next. Its intended benefit, admitting same-scope structure (headings, siblings, figure text) that previous/next cannot reach, was not exercised by these examples.

\emph{E4 visual input} (Table~\ref{tab:e4}). On these four questions and with this generator, structured OCR text was more accurate than full-page images (0.75 vs.\ 0.63) with half the leakage, while using about one fifth of the prompt tokens (616 vs.\ 2{,}934; 2{,}760 visual tokens per page) and of the KV-cache memory (34 vs.\ 160\,MiB); region crops alone were the weakest input. OCR text only and OCR + caption pods reached the same accuracy (0.75) and leakage (0.10); on these questions the pod structure added no accuracy over plain OCR text, at 106 more prompt tokens. The subset gives the pods little to work with: only P013 has a multi-column table grid (which plain OCR text, rebuilt from the same cells, already lists in row order), P028 is a bullet list, P039 a two-column table, and P040 a two-level header. All four inputs failed P040, the multi-level header case above, which the key-value metric alone would have scored as correct. Testing whether pods help the model read table structure needs questions on multi-column, multi-header grids.

\emph{E1 evidence format} (Table~\ref{tab:e1}). All formats cited only gold sources, breadcrumbs gave the most complete citations with gold evidence, and full pods cost the most tokens without a gain. The evidence-format experiment was conducted on four text-oriented questions whose gold evidence contains no table, so the table rendering of the pods was not exercised. Therefore, the results should be interpreted as illustrative rather than conclusive evidence of the superiority of Hierarchical Evidence Pods. In this subset, full pods did not consistently outperform simpler evidence representations. We also ran E1 with gold evidence on five table questions whose tables have cell-aware grids (P006, P008, P013, P015, P048). Every format returned the correct values for P006, P008 and P013. On P015 full pods gave an incomplete answer (the leak location, partly in Chinese, without the remedy) while the other formats gave both parts; on P048 the pod formats (D, E) listed two of the four part numbers, flat text three, and JSON and Markdown all four (key-value recall 0.875 for full pods vs.\ 0.938 for flat text; citation recall 0.80 vs.\ 0.90), at 697 vs.\ 480 prompt tokens. Flat text (A) already lists each table row on one line, so this compares grid serializations with row-wise text rather than structure with no structure; on these simple tables row-wise text was sufficient, and the pods gave no gain. A broader evaluation involving hierarchical tables, merged cells, and conditional footnotes is required to quantify the contribution of the proposed serialization.

\section{Discussion and Limitations}
\textbf{Structure as text.} The results are consistent with moving structure analysis offline. Once tables are delivered as grids and figure text as OCR with caption candidates, the generator reached 0.800 accuracy in the main flow with no image in its prompt, and in the four E4 examples it answered more accurately from OCR text than from full-page images at a fraction of the prompt length. These findings concern Qwen2.5-VL-7B given text-only input, not a language model without a vision encoder, and the E4 comparison covers four questions; they show that a VLM can work from structured text, not that vision is unnecessary in general. The design rationale for the pods is that plain OCR text cannot keep a table's structure: once a table is read line by line, which value belongs to which row, column, header level or merged cell is left for the model to guess, whereas a grid with declared headers and spans states it explicitly. Prior work shows that table serialization strongly affects how well LLMs read tables~\cite{sui2024table}. We therefore expect the pods to help most on multi-column and multi-level tables; the pilot shows that the tables reach the generator (all 21 question--table pairs were in its context), but on five simple table questions the grid form did not read better than row-wise text (Sect.~\ref{sec:errors}), so its benefit on complex tables is left to the full evaluation.

\textbf{Image input and expansion.} The generator is a 7B quantized VLM used zero-shot, so its weak reading of images (Table~\ref{tab:e4}) reflects an untuned model rather than the value of visual evidence; crops in particular lose the labels and headings that the pods keep. We therefore treat images as an offline and retrieval resource here; attaching a crop only where the pods lack text, such as unresolved tables, needs a stronger or adapted VLM and is left for future work. Graph expansion helps most when retrieval returns part of the evidence, and restricting it to the seed's heading scope avoided filling the budget with irrelevant siblings, although simple previous/next expansion was cheaper still on the four examples.

\textbf{Limitations.}\label{sec:limitations} (i) A table whose grid fails validation is published without text, so a text-only generator cannot read it and only an image crop remains. (ii) The three unresolved error types of Sect.~\ref{sec:errors}---footnote scope, multi-level table headers and incorrect heading assignment---remain. (iii) \texttt{RELATED\_PASSAGE} similarity links include noise (shared URLs, boilerplate) and are therefore presented only as proposals. (iv) Answers are checked for citation IDs and format, not by an independent semantic verifier, and 11 of 98 claims were unsupported by their citations. (v) The pilot uses one generator, one run per configuration, LLM-assisted grading reviewed by the first author but without a second, independent grader and documents seen during development; five of 50 questions were answered in a second run, four after a temporary server outage and one after the output-language check was removed; the ablations are worked examples on four or five questions rather than full-scale comparisons, and no run without the ColPali channel was made. (vi) ``Text-only'' conditions used Qwen2.5-VL without images rather than a model lacking a vision encoder. Future work extends the evaluation to 200--300 questions on unseen documents with a second grader, a text-only LLM, a no-ColPali ablation and full-scale format and expansion ablations on table-heavy questions.

\section{Conclusion}
The results demonstrate the feasibility of performing document structure analysis offline and providing a generation model with compact, source-grounded textual evidence. The proposed pipeline achieved promising retrieval and question-answering performance on a technical-document pilot set. Controlled examples suggest potential benefits of scope-aware expansion and structured text representations, although larger and independent evaluations are needed to establish their generalizability.
